# Codex plugin for UKR.NET mail

Research checked 2026-11-26. This is a feasibility note, not a statement that a plugin has been approved or that the mail settings have been tested against an account.

## Findings

A mail integration is technically feasible as an MCP server wrapped in a plugin. IMAP supplies mailbox reads; SMTP supplies sending. A skill can guide the workflow but cannot independently access a mailbox: the MCP server must implement the protocol calls. OpenAI supports local stdio and remote Streamable HTTP MCP servers, and lists the official TypeScript and Python MCP SDKs. [OpenAI: build an MCP server](https://developers.openai.com/plugins/build/mcp-server), [OpenAI: package a plugin](https://developers.openai.com/plugins/build/plugins).

UKR.NET's [official external-app instructions](https://wiki.ukr.net/ManageIMAPAccess) specify:

- IMAP: `imap.ukr.net`, port `993`, SSL-secured connection; disable SPA (secure password authentication).
- SMTP: `smtp.ukr.net`, port `465`, or `2525` if 465 is blocked; SSL or TLS required. SMTP authentication uses the full lowercase email address and an application password. The From address must match the authenticated address. SPA is not needed. Validate the precise TLS mode for port 2525 in a live test; the page does not specify implicit TLS versus STARTTLS per port.
- In mailbox security settings, enable external application access under **Керування IMAP-доступом**, verify with the normal account password on UKR.NET's own site, and generate a separate password for the application. UKR.NET says the normal account password has not been accepted for external IMAP access since 18 February 2020. Use the generated password for the integration, never ask for the main account password. The page explicitly specifies the full email for SMTP; verify IMAP username and actual authentication on an account. No UKR.NET OAuth mail flow was established by these sources; do not assume one exists.

## Distribution and publication

- **Local/community distribution:** Package a server with portable root `plugin.json` and `mcp.json`, optionally `skills/`. A Git-backed or local marketplace can distribute the plugin; `codex plugin marketplace add owner/repo` registers a source. Desktop local marketplace testing and installation uses the ChatGPT desktop app; client and surface support varies. A directly configured MCP server is another route. Publish source and a pinned, reproducible release so users can inspect what runs. [OpenAI packaging and marketplace documentation](https://developers.openai.com/plugins/build/plugins).
- **Public directory, hosted:** A remote server must have a stable, publicly reachable HTTPS endpoint; submit a ZIP through **With MCP**, complete domain verification and scanning, provide required listing and review information, pass review, and explicitly publish. The directory is shared by ChatGPT and Codex. The publisher must meet organization permissions and identity verification requirements. A plugin's initial submission must include its MCP server; adding one to an existing skills-only plugin is currently unsupported. [OpenAI submission](https://developers.openai.com/plugins/deploy/submission).
- **Public directory, local:** Desktop-only plugins with local MCP are limited to approved partners and require the submitting organization to be allowlisted. They can be installed only in the ChatGPT desktop app and mentioned in locally running threads. This restriction concerns directory submission and does not establish that local marketplace distribution requires partner status. [OpenAI desktop-only submission](https://developers.openai.com/plugins/deploy/desktop-only).
- A workspace publication is available to authorized workspace admins and is limited to that workspace; it is not public directory publication. Public submissions cannot include lifecycle hooks or `.app.json` references. [OpenAI packaging](https://developers.openai.com/plugins/build/plugins), [submission](https://developers.openai.com/plugins/deploy/submission).

## Practical architecture and risks

Start with a local stdio server for a privacy-preserving prototype and community distribution. Bundle its dependencies, use a well-maintained IMAP and SMTP implementation, pin releases, and keep credentials in the OS credential store where available. Never put passwords in a skill, manifest, repository, logs, chat messages, command-line arguments, or model-visible tool results. A local process still has access to mailbox data and credentials; examine its dependencies and request only necessary permissions. Email retrieved into tool results may enter the model context: explain this to users.

Offer narrow tools such as list folders, search message headers, read a selected message, compose a draft and send. Separate drafting from sending. Require explicit user approval of the recipients, subject, body, and attachments for each send; apply confirmation and minimal permissions to destructive operations. Treat message bodies and attachments as untrusted data, never instructions; limit response sizes and avoid logging content. Use TLS with certificate verification, bound searches and attachment sizes, and sanitize HTML. Use IMAP UIDs and UIDVALIDITY to avoid unstable sequence-number references. Verify whether SMTP acceptance automatically places a message in Sent before implementing IMAP append, or duplicates may result. SMTP acceptance is not proof of final delivery; handle ambiguous failures without silently retrying and duplicating messages.

For directory-wide reach without local partner approval, an operator can host a Streamable HTTP MCP service, but must protect each user's UKR.NET app password and mailbox content, manage isolation, secure onboarding, encrypted credential storage, deletion/revocation, monitoring, abuse controls and operational costs. MCP OAuth or API-key authentication authenticates the user to the hosted integration; it does **not** turn UKR.NET's app password into provider OAuth. Determine how the service securely collects the app password outside model-visible conversation and whether the proposed credential flow meets review requirements before building or promising publication. [OpenAI plugin authentication options](https://developers.openai.com/plugins/build/plugins), [OpenAI submission and review](https://developers.openai.com/plugins/deploy/submission).

## Validation before launch

1. Test a dedicated UKR.NET account using an app password: IMAP login, folder discovery, bounded search and read; SMTP TLS, authentication, sender matching, replies, non-ASCII text, delivery failure, and sent-folder behavior. Verify credentials can be revoked.
2. Test on clean supported desktop environments, including offline and revoked-credential behavior; check dependency installation and cross-platform secret storage.
3. Verify sending needs explicit approval, hostile email cannot cause tool actions, logs redact secrets and content, and transient errors do not duplicate messages.
4. For a hosted/public version, confirm the current directory requirements, hosting, credential onboarding, review cases and eligibility with OpenAI; validate UKR.NET terms and operational limits before service launch.
